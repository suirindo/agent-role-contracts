# 候補が、自分のPASSを作るチェックを管理できるか

[English](https://github.com/suirindo/agent-role-contracts/blob/main/experiments/failure-lab/03-candidate-controls-own-check.md)

この文書は英語版の要約です。出力全文と詳しい説明は英語版が正本です。

マージゲートは、どの候補にも同じコマンド`node scripts/test.mjs`を実行します。コマンドは変わりません。しかし、そのコマンドが呼ぶスクリプトは候補の中にあります。候補が自分のテストステップを書き換えると、テストを1つも実行せずに成功を報告でき、ゲートには以前と同じPASSが記録されます。この例では、使い捨てのディレクトリでそれを再現し、候補が管理できないチェックと並べます。

この事例は、Iliya Oblakov氏からいただきました。2026-11-24に、[第2回のDEVの議論](https://dev.to/netsujo/arc-failure-lab-2-a-signed-pass-for-the-wrong-commit-23lg#comment-3m9mf)で、自分のローカルのゲートで`make test`と候補側のMakefileを使って測った結果を報告されました。2026-11-27に利用を了承され、私たちはクレジットを付けることにしました。議論の出発点になった偽ACCEPTの記事は[こちら](https://dev.to/iliyaoblakov/i-forged-a-codex-accept-with-four-lines-of-text-and-my-merge-check-passed-it-4odk)です。下のフィクスチャは、Node.jsで作った私たち独自の合成の翻案で、氏のMakefileではありません。氏の結果は氏の報告であり、私たちは再実行していません。

これはホストのゲートの実験です。ARC（Agent Role Contracts）は実行しません。

```sh
git clone https://github.com/suirindo/agent-role-contracts.git
node agent-role-contracts/experiments/failure-lab/03-candidate-controls-own-check/run.mjs
```

前提条件はNode.js 22以上です。ほかに導入するものはなく、clone後にネットワークは使いません。デモは一時ディレクトリにだけ書き込み、終了時に削除します。エージェントもCIも実行しません。

3つの合成の候補が`add(a, b)`を実装します。それぞれテストとテストステップを持ちます。ケースBは、コードが誤っていて、テストステップを「all tests passed」と表示して終了コード0で終わるように書き換えています。

| 候補 | 自分のテストステップ | 信頼できるチェック |
| --- | --- | --- |
| A：正しいコード | PASS | PASS |
| B：誤り、ステップ書換え | PASS | FAIL (exit 1) |
| C：誤り、正直なステップ | FAIL (exit 1) | FAIL (exit 1) |

ケースBでは、動作が誤っているのに、候補自身のステップはPASSを報告します。信頼できるチェックは、どの候補のディレクトリの外にもあります。`src/add.mjs`を読み込んで`add()`を自分で呼ぶので、候補のテストやテストステップは読みません。

## この例が示さないこと

- 3つのケースで、外側のコマンドは同一です。コマンドラインが同じでも、チェックが同じとは限りません。
- ここでの信頼できるチェックは、同じユーザーが動かす1つのローカルプロセスです。実際のランナーの運用上の独立性は示しません。
- 3つの検証を持つ1つのオラクルは、`add()`が正しいことの証明ではありません。
- 実際のCI、ワークフローファイル、ランナーの管理者、依存物、キャッシュは試していません。キャッシュの事例は別の後続で、`NOT_RUN`です。
- ARCは実行していないので、この例からARCの出力について言えることはありません。

## ARCが確かめたことと、確かめていないこと

この例ではARCを実行していません。判定は、候補の外にあるチェックによるもので、ARCによるものではありません。変更されたテストステップのパスに`explain`も実行していないので、報告できるARCの結果はありません。パスが宣言した範囲の中にあったとしても、PASSが自己生成であることは変わりません。ARCはテストの意味を判断せず、テストスイートを変更不能にもしません。関連する議論は[#138](https://github.com/suirindo/agent-role-contracts/issues/138)にあります。

## 同じコマンドが同じチェックにならない理由

コマンドを信頼するゲートは、連鎖を信頼しています。それぞれに管理者がいます。

1. 外側のコマンドやワークフロー。このフィクスチャではゲート側が持ちます。
2. 呼び出されるスクリプト。`scripts/test.mjs`は候補が持ちます。
3. テスト定義。`tests/add.test.mjs`は候補が持ちます。
4. ランナーへの入力：依存物、環境、キャッシュ。ここでは試していません。
5. 結果の集め方：ランナーの終了コードか、スクリプトが表示した文字か。ケースBは文字を表示して0で終わります。

どれか1つでも候補のものなら、PASSは候補が自分について述べた言葉かもしれません。

## 新しいcheckoutは実行の同一性ではない

新しいcheckoutは、クリーンな作業ツリーから始まることを示します。実行されたコードが、レビューしたコミットのコードであることは示しません。キャッシュ、生成ファイル、無視されたフォルダー、導入済みの依存物も入力です。この例では試していません。次の候補は、Iliya Oblakov氏が2026-11-27に報告したキャッシュの事例です。同じ更新秒、同じファイルサイズ、gitignoreされたキャッシュフォルダーのせいで、古い結果がPASSした事例です。これは`NOT_RUN`で、ここに挙げることは公開日の約束ではありません。

## 自分のゲートで試す

実際のパイプラインではなく、使い捨てのリポジトリで試してください。

1. 外側のコマンドが指すファイルを、すべて書き出す。
2. そのうち、候補が変更できるものに印を付ける。
3. 判定が、候補が変更できないランナーと入力から出ていて、候補が表示した文字から出ていないことを確かめる。

## 実行結果

出力全文は英語版にあります。2026-11-28に、macOS（arm64）、Node.js v24.11.1で、この記事のマージ前に1回実行しました。デモの終了コードは0です。出力の`FAIL (exit 1)`は、1つのチェックの結果で、デモ自身の終了コードとは別です。LinuxとWindowsでは実行していません。この例は、Netsujoのメンテナーが作った合成の例で、第三者の検証ではなく、実行時の強制も示しません。
