# 自分のリポジトリで最初のタスクを書く

[English](FIRST-TASK.md) | 日本語

[単独のプロジェクトでの確認](README.ja.md#1-単独のプロジェクトで試す)が通ったところから始めます。現在の権限に収まり、実装者とは別のレビューを必要とする、`src/` 以下の実際のコード変更を選んでください。別のパスや役割が必要な場合は、既存の権限レビューへ戻します。この手順では `.arc/bundle.json` を変えません。

## 実行する前に作業を記述する

ARC を使う側のプロジェクトのルートで、エディターを使って `.arc/task-first.json` を新規作成します。同名のファイルがすでにあれば、別の名前を選んでください。次の例をもとに、ID、目的、パス、受入条件を自分の実際のタスクに置き換えます。

```json
{
  "schema_version": "0.1",
  "id": "greeting-fallback-1",
  "type": "code-change",
  "objective": "src/greeting.mjs で名前がない場合の挨拶を更新する。",
  "inputs": { "scope": "src/greeting.mjs" },
  "acceptance_criteria": [
    "名前がない場合も例外を出さずに挨拶する。",
    "既存の挨拶のテストが通る。",
    "実装者とは別のレビュアーが変更を確認する。"
  ]
}
```

| フィールド | 記述する内容 |
| --- | --- |
| `id` | タスクとそのレビューを対応付けられる、ほかと区別できる識別子 |
| `type` | `code-change` のままにする。変更しない bundle に宣言済みの経路を選ぶため |
| `objective` | 求める結果を自分の言葉で記述する |
| `inputs.scope` | 許可された `src/**` 内の相対パス、またはディレクトリ配下の範囲を一つ記述する。実際の変更との照合は別途行う。書き方は[scope の書き方](#scope-の書き方)を参照 |
| `acceptance_criteria` | 結果と必要なレビューを確認できる条件を記述する。ここに書くだけでテストやレビューが実行されるわけではない |

`schema_version` は `0.1` のままにします。宣言をチェックするためだけに、例のソースファイルを作成する必要はありません。PASS は、ファイルの存在、テストの成功、承認の取得、作業の実施を証明しません。

## scope の書き方

公開版 1.0.0 の `inputs.scope` は**一つの文字列**です。`src/greeting.mjs` のような一つのファイルパスか、`src/greeting/**` のように `/**` で終わる一つのディレクトリ配下の範囲を書きます。区切りは `/` を使い、先頭に `./` や `/` は付けません。末尾の `/**` 以外のワイルドカードは使えません。リポジトリ全体を表す `**` も使えません。

次の値は、同梱 bundle（`src/**`）を変えずにチェックすると、`task/inputs/scope` で終了コード 1 になります。導入済みのチェッカーは `TASK_WRITE_SCOPE_INVALID` のどの値にも同じメッセージを返すため、原因はこの表で確認してください。

| 書きがちな値 | 公開版 1.0.0 の結果 | 代わりに書く値 |
| --- | --- | --- |
| `./src/greeting.mjs` | `TASK_WRITE_SCOPE_INVALID` | 先頭の `./` を外した `src/greeting.mjs` |
| `src/` | `TASK_WRITE_SCOPE_INVALID` | 配下全体なら `src/**`、それ以外は実際に変えるファイル |
| `src\greeting.mjs` | `TASK_WRITE_SCOPE_INVALID` | Windows を含むどの OS でも `/` 区切りの `src/greeting.mjs` |
| `src/**/*.mjs` | `TASK_WRITE_SCOPE_INVALID` | `src/greeting/**` などのディレクトリ配下の範囲。使えるのは末尾の `/**` だけ |
| `src/greeting.mjs,src/farewell.mjs` | `TASK_WRITE_SCOPE_INVALID` | 両方を含む最小のディレクトリ配下の範囲、またはファイルごとに別のタスク |
| `["src/greeting.mjs", "tests/greeting.test.mjs"]` | `SCHEMA_TYPE` | 文字列を一つだけ書く。[複数のパスにまたがる場合](#一つの変更が複数のパスにまたがる場合)を参照 |
| `**` | `TASK_WRITE_SCOPE_INVALID` | `src/**` など、許可範囲内の名前付きディレクトリ配下の範囲 |
| `tests/greeting.test.mjs` | `TASK_WRITE_SCOPE_OUTSIDE_AUTHORITY` | 構文は正しいが、同梱の許可範囲は `src/**` だけ。[複数のパスにまたがる場合](#一つの変更が複数のパスにまたがる場合)を参照 |

`.github/` や `src/.env` のように `.` で始まる要素を含むパスは、[公開版 1.0.0 で使える scope](README.ja.md#公開版-100-で使える-scope) の表に従います。実際に変えるパスを隠すために scope の名前を変えないでください。

### 一つの変更が複数のパスにまたがる場合

- **すべてのパスが、許可範囲内の一つのディレクトリの下にある場合**：`src/greeting/**`、モノレポなら `packages/app/**` のように、そのディレクトリ配下の範囲を書きます。範囲は実際に変えるファイルより広く宣言されるため、実際の差分とタスクの照合は引き続き行ってください。
- **`src/` と `tests/` のように、リポジトリ直下の別のディレクトリにまたがる場合**：1.0.0 では、一つのタスクで両方を宣言できません。同梱の許可範囲も `src/**` だけです。ディレクトリごとにタスクを分け、それぞれをチェックします。`src/**` 以外のタスクが通るのは、権限の責任者が既存のレビューを経て bundle の変更を承認した後だけです（例：`tests/**` の追加）。この分け方が実際の作業に合わない場合は、既存のレビューを維持し、その制約を記録してください。

PASS を得るために権限を広げたり、変更の一部しか含まない scope を選んだりしないでください。変更の一部に対する PASS は、残りの部分について何も示しません。

## 正常な宣言、拒否、修復を確認する

利用側のプロジェクトのルートで次を実行します。別のファイル名を選んだ場合は、`--task` の値も合わせてください。

PowerShell では `npx.cmd` を使い、コマンド直後の `$LASTEXITCODE` で終了コードを確認します。macOS／Linux の POSIX shell では `npx` と `echo $?` を使います。次のコマンドは一行のまま実行できます。

```sh
npx --no-install agent-role-contracts explain --bundle .arc/bundle.json --task .arc/task-first.json --format text
```

1. `src/` 内の正確な scope なら、PASS と終了コード 0 を返す想定です。通らない場合は、[scope の書き方](#scope-の書き方)を確認し、次に[診断と修復の一覧](README.ja.md#診断から修復する)を確認します。
2. 本来の scope を控えてから、`inputs.scope` だけを一時的に `secrets/private.json` へ変えます。同じコマンドを再実行し、終了コード 1 と、`task/inputs/scope` の `TASK_WRITE_SCOPE_OUTSIDE_AUTHORITY` を確認します。これは境界の確認用の変更であり、その範囲で作業する指示ではありません。
3. 本来の正確な scope に戻して再実行します。再び PASS と終了コード 0 になることを確認してください。差分を確認し、`.arc/bundle.json` が変わっていないことも確かめます。意図的な拒否を解消するために権限を広げないでください。

入力ファイルを読めない、コマンドやオプションが正しくない、といった問題では終了コード 2 になります。宣言の合否に到達していないため、エラーを直して同じファイルを再確認します。

既存の `npm run arc:check`、hook、CI の例が読むのは `.arc/task.json` です。`.arc/task-first.json` を作っただけでは切り替わりません。連携先を導入するときは、設定をレビューして、確認したいタスクのファイル名に合わせてください。既存の宣言を残し、実際のコマンドやスクリプトが指定しているファイル名を確かめます。

ここまでで確認できたのはタスクの宣言です。必要な承認を得て、普段の権限管理とレビューの手順に従って実作業を行い、その結果を記録してください。異なる二つ目の実タスクでの再利用は、[実務評価キット（英語）](../external-evaluation/README.md)で扱います。上の三回のチェックを、三つの実タスクや導入実績として数えることはできません。
